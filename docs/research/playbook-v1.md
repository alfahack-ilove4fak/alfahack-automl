**Итог:** 11 гипотез в `research/playbook.yaml` (было 5). Порядок — по выигрышу на честной отложенной части; **v1.1** — порядок перепроверен на 7 задачах (раздел в конце). 4 кандидата выброшены. Все `params` уже поддерживаются `ml/experiment.py` — новых ключей нет.

## Как мерили

Каждая гипотеза — две оценки против бейзлайна на обеих публичных задачах:
- **cv** — ровно то, что видит агент: `ml.experiment.run_experiment` (5 фолдов, KFold / StratifiedKFold);
- **honest** — одно обучение тем же кодом модели на отложенной части **без утечек** из EDA (`docs/research/eda.md`): регрессия — последний год train (test — следующий год), классификация — фолд StratifiedGroupKFold, где полные дубликаты вместе.

## Выводы

1. **cv и honest часто расходятся по знаку.** `lgbm_extra_trees` — худший по cv на обеих задачах и лучший по honest на регрессии (42.5 против 48.4). `lgbm_big_leaves` и `lgbm_slow_lr` — наоборот. Пока агент сравнивает гипотезы на KFold, он будет выбирать «запоминающие» модели. Это аргумент за D1 из ADR 0008 и задачу ml M-L2-1 (схема валидации через `params`).
2. **Регуляризация выигрывает на обеих задачах.** Сглаживание листьев, L1/L2, мелкие деревья, меньший шаг с регуляризацией — устойчивый плюс на honest. Универсальная идея: когда test отличается от train, модель «проще» переносится лучше.
3. **`balanced_classes` реабилитирован.** В журнале 20.10 он записан в проигравшие по cv, но на честной части — лучший для классификации (+9.8%). Дубликаты частых классов (Generic — 96% дубликатов) завышают cv модели без весов.
4. **Комбинации работают** (`log_target_slow`, `lgbm_slow_regularized` — лучше своих частей на honest). Пока цикл не складывает выигрыши (issue #87), комбинации нужны в playbook.

## Ограничения (честно)

- **Две задачи.** Универсальность проверена только на public; когда в `dev` появятся `tasks/practice/` (R-L1-3), стенд подхватит их сам — перепроверить порядок.
- **honest — одна отложенная часть**, без разброса. Разница меньше ~1–2% (разброс фолдов на multiclass ≈ 1.7% от среднего) — скорее шум; поэтому `lgbm_fine_bins` в конце.
- Время в стенде искажено: часть прогона шла параллельно с другими процессами на 4 ядрах (бейзлайн multiclass — 699 с вместо ~100 с). На скоры это не влияет.
- Ранняя остановка в `run_experiment` идёт по тому же фолду, на котором считается скор, — cv немного оптимистична для всех гипотез одинаково.

## Что не вошло, потому что нужны новые `params` (для ml и agent)

| Идея | Что нужно | Кому |
|---|---|---|
| Схема валидации по времени / группам | `params.cv` или выбор до цикла (ADR 0008, D1) | ml (M-L2-1) |
| Флаги пропусков, редкие категории → «other», частотное кодирование | библиотека преобразований | ml (M-L2-2) |
| Целевая функция под метрику (MAE → `objective: l1`, RMSLE → log) | фильтр гипотез по метрике в `_applies` | agent |
| CatBoost / XGBoost | `model: catboost` | ml (M-L1-1, M-L1-2) |
| Условия по профилю данных (сдвиг во времени, дубликаты, мало строк) | предупреждения в `DataProfile`, новые `requires` | ml + agent (issue #92) |

**Выводы v1.1**
1. **`log_target` — универсальный** для скошенного неотрицательного таргета: честный выигрыш на всех трёх регрессиях (на продажах +7.6%). Поднят с 9-го места на 2-е.
2. **`lgbm_slow_regularized` — самая устойчивая** (5 из 7). `lgbm_smooth_leaves` хороша только на публичных задачах — опущена (3 из 7).
3. **CV снова врёт.** На 70 парах «гипотеза × задача» (все 15 кандидатов v1 на public + 11 гипотез на тренировочных) знак выигрыша по CV и честно расходится в **25 случаях**; из 20 гипотез, которые агент принял бы по CV (выигрыш > 0.25·std), **4 честно хуже бейзлайна**. `lgbm_extra_trees` в среднем проигрывает по CV (−1.1%), но выигрывает честно (+2.0%).
4. На маленьких задачах (cancer 398 строк, diabetes 309) разница гипотез почти вся в шуме: разброс CV на diabetes — 6.7% от среднего.

**Ограничение стенда:** колонка времени ищется только среди целых чисел, поэтому в `sales` (дата строкой) честная часть — группы дубликатов, а не «последний период». На этой задаче test позже train — честная оценка для неё всё ещё оптимистична. Нужен разбор дат в `DataProfile` (P1 в ADR 0008).
