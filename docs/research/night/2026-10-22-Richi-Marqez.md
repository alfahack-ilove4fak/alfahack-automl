### Как агент тратит бюджет (5 мин)

Цикл может идти до ≈ 255 с (резерв 15%), но **9 из 10 задач закончились «Гипотезы закончились» на 156–195 с**;
только multiclass упёрся во время. То есть даже на 5 минутах 25–40% бюджета не используется.

Почему так (по логам и `agent/fallback.py`):
1. Playbook — 15 гипотез, на малых данных они проходят за секунды (diabetes: 13 гипотез за 3 с).
2. Запасные направления (#200): xgboost / catboost / hist_gb + Optuna. Optuna предлагается, только пока
   `0.3 · остаток ≥ 30 с` (`OPTUNA_MIN_SECONDS`), то есть цикл всегда выходит, когда до конца цикла < 100 с.
3. **Ошибка: Optuna повторяется под новыми id.** id запасной гипотезы — хэш params, а в params лежит
   `optuna.timeout = round(0.3 · остаток)`. Остаток меняется → новый хэш → «новая» гипотеза. На diabetes —
   **≈ 70 запусков одной и той же Optuna** (итерации 14–84), на cancer — 14 (каждые ~10 с с 15-й по 149-ю с).
   На платформе (3 ч) timeout = 600 с, пока остаток ≥ 2000 с — там id стабилен, а повторы начнутся
   только в последние ~33 минуты. Владелец — agent (@n0h4ndy); исправление: не класть `timeout` в ключ повтора
   (сравнивать `base_params` без `optuna.timeout`) — 1–2 строки.
4. Источник запасных гипотез в логе — `[playbook]` (поле `source` по умолчанию), хотя их придумали правила;
   итог «Решения LLM» это не путает, но читать лог сложнее.

### Плохая LLM: поддельный сервер

Настоящего ключа нет, поэтому поведение агента при плохой LLM проверено поддельным OpenAI-совместимым
сервером на localhost (`research/night/fake_llm.py`, режимы ниже), задача `tasks/practice/cancer_binary_auc`,
прогон — `research/night/llm_faults.py` (агент запущен без `LLM_MOCK`, `OPENAI_BASE_URL` → localhost).

**Медленный поток (`trickle`: 1 символ раз в 3 с) — ❌ потеря всей задачи.**
Бюджет 180 с: агент отправил первый запрос (LLM-аналитик задачи, `MAX_WAIT = 90 с`) на 1.7 с и **висел
на нём 170 с — до сторожа**. Шаг 0 (тривиальный ответ) так и не записан, бейзлайна нет; сторож скопировал
`sample_submission.csv` → **ROC-AUC 0.5**. Лог: `[1.7s] LLM: модель fake-model…` → `[172.1s] Сторож сработал`.
- Почему: `_create_with_retries` ставит httpx `timeout = остаток до дедлайна`, но для потока это таймаут
  **на каждое чтение**, а не на весь ответ; пока байты идут, запрос не обрывается. `MAX_WAIT` и ¼ остатка
  бюджета для потока не работают.
- Насколько реально: «рассуждающая» Qwen шлёт токены рассуждений потоком; запрос аналитика — до
  600 + 6000 токенов. При 20 ток/с это ≈ 5.5 мин вместо 90 с, при 2 ток/с (сервер под нагрузкой в финале,
  когда все команды гоняют скрытые задачи) — ≈ 55 мин **до шага 0**.
- Исправление (agent, @n0h4ndy; 3–5 строк): в `_collect_stream` проверять дедлайн на каждом чанке и
  закрывать поток; и (captain, @thenlaooo) писать тривиальный ответ **до** запроса аналитика —
  сейчас `parse_task` с LLM идёт раньше шага 0.

**Зависшая LLM (`hang`: соединение есть, ответа нет), бюджет 3 ч, наблюдение 12 мин — ⚠️ тратит время.**
Аналитик ждал 90 с (его лимит) → шаг 0 на 92 с, бейзлайн на 107 с. Первый запрос гипотез висел
**497 с** (111 → 608 с): 4 попытки по 120 с + паузы 2/5/10 с — при большом остатке бюджета лимит
«¼ остатка» не действует (`time_limit` → None, если ¼ остатка ≥ 360 с). За 12 мин — 2 итерации
(без LLM весь playbook на этой задаче — секунды). Ответ валиден (AUC 0.983). На 3 часах агент будет
≈ 8 мин ждать на каждом запросе с паузой 120 с после 3 сбоев подряд — до половины бюджета в ожидании.
Предложение (agent): потолок одного запроса 60–90 с независимо от остатка и выключать LLM до конца
прогона после 3 таймаутов подряд (а не пауза 120 с).

При бюджете 180 с цикл LLM не зовёт вовсе (¼ остатка < `MIN_CALL_SECONDS` = 60 с), поэтому «мусор» и
«плохой код» прогнаны с бюджетом 420 с.

| Режим | Итог | Что видно |
|---|---|---|
| `garbage` (текст без JSON), 420 с | ✅ AUC 0.983, 22 итерации | 11 запросов — все мусор, агент **продолжал спрашивать**: 16.5 тыс. токенов впустую (тай-брейк!) |
| `badcode`, 420 с | ✅ AUC 0.983, 23 итерации | модель `superboost9000` → FAILED; `n_folds='five'`, `num_leaves=1e6` → критик; Optuna на 1e5 испытаний → «не успеет»; `time:no_such_column` → пропуск; код признаков `while True` → песочница убила через 120 с; аналитик с несуществующей колонкой и метрикой — не принят |
| `refused` (порт закрыт), 180 с | ✅ AUC 0.983 | шаг 0 только на **18 с**: повторы 2 + 5 + 10 с идут до шага 0 |
| `trickle`, 180 с | ❌ AUC 0.5 | см. выше: висит до сторожа |
| `hang`, 3 ч (12 мин) | ⚠️ AUC 0.983 | 497 с на один запрос |

Предложение (agent): после 2–3 мусорных ответов подряд выключать LLM до конца прогона (экономия токенов).

## Фаза 5 — анализ и точки роста

### Топ-10 проблем

Порядок — (вероятность на скрытой задаче × потеря баллов) / сложность исправления.
Воспроизведение «чужих» задач: `uv run python research/night/make_alien_tasks.py`, затем
`uv run python research/night/run_alien.py --minutes 5 --only <задача>`.

**1. Метрику решает регулярка, а не LLM; в реестре нет F-beta.** (agent @n0h4ndy + qa @dzigoku-ku)
- Сломано: MAPE словами → `mae`; «каппа Коэна с квадратичными весами» → не найдено → `f1_macro`;
  «F2 score (F-beta)» → `accuracy`; «площадью под ROC-кривой» → не найдено (спасло умолчание).
  `task_analyst.reconcile` меняет метрику, только если регулярка ничего не нашла: «поиск по тексту нашёл …:
  оставлен поиск».
- Цена: ordinal_kappa — QWK 0.7963 против LightGBM 0.7986 → **0 баллов**; english — F2 0.004 против 0.129.
- Задачи: `ordinal_kappa_words`, `english_noisy_fbeta`, `mape_in_words`.
- Исправление: при расхождении брать метрику LLM, если она в реестре и регулярка нашла свою вне фраз-маркеров;
  добавить `fbeta@β` (как `pinball@α`) и алиасы «каппа Коэна», «площад* под roc», «… в процентах».

**2. Цель обучения не под метрику (MAE / MAPE / квантиль учатся на L2).** (ml @marenkov17 + research)
- Сломано: нет ни одной гипотезы с `objective`; дополнительные таргеты учатся `baseline_hypothesis()` (L2).

- Задачи: `multitarget_pinball90`, `tasks/practice/claims_regression_mape_rowno` (харнесс).
- Исправление: цель по умолчанию из метрики в `ml/experiment.py` (pinball@α → quantile α, MAE/MedAE → l1,

### Топ-5 идей роста

**1. Цель обучения из метрики — по умолчанию.**
- Гипотеза: MAE/MAPE/квантиль на «своей» цели дают больше, чем любой перебор гиперпараметров.
- Проверка за час: ветка в `ml/experiment.py` (objective по `spec.metric`) → харнесс на claims и diabetes
  + `run_alien.py` на `multitarget_pinball90`, `mape_in_words`, `semicolon_decimal_mae`.
- Ожидаемо: pinball +36 баллов, MAPE +8.5 (замерено LightGBM с целью); на RMSE/классах — без изменений.
- Риск подгонки под public: **низкий** — решение выводится из метрики, а не из данных.

**2. Простаивающие ≈ 140 мин: усреднение и ансамбль вместо выхода из цикла.**
- Гипотеза: когда гипотезы кончились, (а) бэггинг лучшей модели по 5 seed, (б) простое среднее OOF
  2–3 лучших моделей разных семейств (у нас уже есть xgboost/catboost/hist_gb), (в) Optuna с большим
  числом испытаний на схеме прогона — дают +1–3% метрики при том же правиле принятия (t ≥ 2).
- Проверка за час: запасное направление «seed-бэггинг лучшего» → 60-мин прогон regression + харнесс
  на multiclass и digits (там catboost «почти прошёл»: t = 1.50).
- Риск: средний — множественные сравнения (см. повторы Optuna): считать попытки и поднимать порог t.

**3. LLM принимает решения там, где правила слабы.**
- Сейчас LLM-аналитик называет `time_column` и `group_column`, но они идут **только в notes** —
  `choose_validation` их не видит; метрику LLM переопределить не может (проблема 1).
- Гипотеза: принимать от LLM (с проверкой по данным) метрику при расхождении, колонку времени/групп для
  схемы валидации и цель обучения; LLM же выбирает следующее направление, когда playbook исчерпан
  (вместо фиксированного списка запасных) — это и есть «агентность», которую будут смотреть вручную.
- Проверка за час: `run_alien.py` с настоящей Qwen на `mape_in_words`, `ordinal_kappa_words`,
  `english_noisy_fbeta` — сколько полей LLM угадала верно и сколько баллов это вернуло.
- Риск: низкий для подгонки, средний — для надёжности (каждое поле проверять по данным).
