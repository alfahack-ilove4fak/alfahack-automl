### 3б. Находки по порядку приоритета
**1. Разделитель CSV только `,` — крах разбора → нулевой ответ (t01, v01, v03).** `pd.read_csv` без `sep`/`decimal` во всех модулях (`agent/task_parser.py`, `solution.py::blind_answer`, `ml/profiling.py`). `;` и TSV читаются как одна колонка → «не удалось определить target» → в `submission.csv` копия `sample_submission.csv` с нулями (MAE 99.6 против 3.2 у LightGBM). Агент при этом выходит с кодом 0 и «валидным» файлом.

**2. Запятая-десятичная при кавычках (v02): числа читаются строками.** Таргет «object», задача определена как multiclass с **2200 классами**, метрика MAE; финальное обучение висело до жёсткого дедлайна (57.8 с из 60), в ответе — константа `-0,00011…` строкой. Спецификация должна была заметить: метрика «value», а таргет parse-able как число.

**3. Нет id в шаблоне ответа (t02).** Шаблон из одной колонки `churned`: `id_column = target = churned`, `KeyError` в `trivial_answer`, в итоге копия шаблона (константа 0.5, AUC 0.5; у LightGBM 0.856). Шаблон без id — «ответ в порядке строк test» — в вебинаре прямо не исключён.

**4. Имена файлов (v06, v07, v08, v09).** Ищутся только `train*.csv` / `test*.csv` / `sample*submission*.csv`. `data_train.csv`/`data_test.csv` → копия шаблона с нулями (MAE 2.68 = нулевой ответ); `learn.csv`/`holdout.csv`/`submission_example.csv` и `TRAIN.CSV` → **вообще нет `submission.csv`** (`rglob("*.csv")` чувствителен к регистру, хотя `re.I` стоит); `.csv.gz` → нет файла. На публичных задачах всё названо стандартно, но «никаких гарантий» (webinar-qa).

**5. Кодировки (v04, v11).** CSV в cp1251 → крах, ответ — копия шаблона. `task.md` в cp1251 → **нет `submission.csv`** (чтение `utf-8` без `errors=`). BOM в CSV и в `task.md` — работает (v05, v12).

**6. Метрики вне реестра (t10, t16 и проба `runs/night/metric_probe.py`).** `find_metric_in_text` вернул `None` для: F-beta/F2, Brier score, MASE, explained variance, Hamming, Jaccard, Spearman, «coefficient of determination»; неверно: «ranked by RMSE» при упоминании MAE раньше → mae; «we used accuracy, but now RMSE» → accuracy (раньше по тексту побеждает); «Cohen's kappa» → qwk (квадратичная; «Linear weighted kappa» → None). **t10:** фраза про «recall counts twice» → метрика `recall` → CV-recall 0.956 = «ставим 1 почти всем» → F2 0.043 (LightGBM с порогом по OOF для F2 даёт 0.083 — вдвое выше; в train всего 46 положительных, оценка шумная). LLM-аналитик должен ловить такие случаи (`closest_metric`), но **без ключа это не проверено**.

**7. Метрика не влияет на функцию потерь (t15).** `ml/experiment.py` не содержит `objective` вообще: MAE, MAPE, pinball и т.д. оцениваются, но модель всегда учится на L2. Квантиль 0.9: агент 0.497 — **хуже константы** (0.479), `objective=quantile` даёт 0.278 (−44%). То же логично для MAE (L1) и MAPE (в README практики: `objective=mape` 0.43 против 0.51 у log). Но **big3m**: чтение CSV и тривиальный ответ — 79 с; CV бейзлайна на подвыборке 500 тыс. строк — **863 с**; финальная модель на 3 млн строк не успела до сторожа (1425 с) → ответ остался средним, хотя CV-модель была. **Пик RAM 7.7 ГБ** при файле 2 ГБ (≈ 2.2 КБ на строку при 55 колонках) → на 32 ГБ предел ≈ 13 млн таких строк. Масштаб: 2 ядра × 25 мин против 8 ядер × 180 мин — у платформы ≈ ×29 по ядро-секундам, так что для 3 млн строк это не риск; для ≥ 30–50 млн — да. Предложение (идея 5): тестовые предсказания фолд-моделей как «бесплатный» промежуточный ответ.

### 4в. Плохая LLM (мок-сервер, не настоящий Qwen!)
Задача `claims` (MAPE). Контрольный прогон без LLM: MAPE на скрытых ответах **0.5049**, лучшая гипотеза `log_target_slow`. Бюджет 5 мин, затем 12 мин для режимов с кодом признаков.

| Сценарий | Бюджет, с | Результат | Время, с | MAPE |
|---|---|---|---|---|
| LLM недоступна (порт закрыт) | 300 | ✅, 1 ошибка в логе, дальше playbook | 202 | 0.5049 |
| Ответ — не JSON | 300 | ✅, гипотез нет, playbook | 209 | 0.5049 |
| Ответ через 100 с (медленная) | 300 | ✅, 1 таймаут, дальше playbook | 249 | 0.5049 |
| «Нормальные» гипотезы | 300 | ✅ | 192 | 0.5049 |
| Мусорные гипотезы (ложный аналитик здесь не вызывался: у задачи есть шаблон) | 300 | ✅ | 162 | 0.5049 |
| Код признаков: **бесконечный цикл** | 720 | ✅ код убит по таймауту песочницы 120 с (×2 попытки) | 551 | 0.5049 |
| Код: цикл на 10⁹ итераций | 720 | ✅ отклонён «все колонки константные» | 546 | 0.5049 |

- При бюджете 5 мин LLM вообще вызывалась один раз: после 4 мин остатка `llm_client` её не зовёт (`До конца бюджета N с — LLM не зовём`). Это правильно для 180 мин, но означает, что **LLM-часть цикла я проверил только при 12 мин**.
- Мок возвращает фиксированные 700 токенов/запрос — реальную стоимость и качество гипотез **не измерял** (нет ключа).
- **Ложный аналитик (`run_liar2.py`, задача без шаблона и без метрики в тексте):** мок-LLM сказал `id_column=cat_a`, `metric=mae`, `target=f0`. Результат: target отклонён правильно («такой колонки нет только в train»), **но `id_column=cat_a` принят** (колонка есть в test, а id был «угадан»), метрика заменена на `mae` для порядковых классов 1–5. Итог: `submission.csv` с колонкой `cat_a` вместо `id` (значения E, D, … — не уникальны) — платформа такой файл не примет. Защита в `agent/task_analyst.py::reconcile` проверяет только «колонка есть в test», не **уникальность** и не соответствие шаблону.

## Фаза 5 — анализ и точки роста

### 5.1. Топ-10 проблем
Порядок: (вероятность встретить на скрытой задаче × потеря баллов) / сложность. Вероятности — моя грубая оценка; вебинар обещал «никаких гарантий» по формату и метрике.

**1. Функция потерь не зависит от метрики** — `ml/experiment.py` (владельцы @thenlaooo @marenkov17).
Модель всегда на L2, метрика только оценивает. Воспроизведение: `.venv/bin/python research/night/objective_probe.py`.

| Задача (повторная 5×3 CV) | L2 | Под метрику | Эффект |
|---|---|---|---|
| claims, MAPE | 0.5909 | `objective=mape` 0.4285 | −27% |
| t15, pinball 0.9 | 0.6119 | `objective=quantile` 0.2828 | −54% |
| diabetes, MAE | 47.19 | l1 46.19 / huber 45.91 | −2.1% / −2.7% |
| t08, MAE | 0.3168 | l1 0.3122 | −1.4% |

В прогоне агента t15 дал pinball 0.497 — хуже константы (0.479). Исправление: ключ `objective` в `params` (MAE→l1/huber, MAPE→mape, pinball@α→quantile, poisson/gamma/tweedie → одноимённые) как первая гипотеза после бейзлайна. Универсально, к public не привязано.

**2. Разбор файлов хрупок** — `agent/task_parser.py`, `ml/profiling.py`, `solution.py` (@n0h4ndy, @marenkov17, @thenlaooo).
`;`, TSV, cp1251, `data_train.csv`, `TRAIN.CSV`, `.csv.gz`, task.md в cp1251 → 9 из 13 вариантов дают нулевой ответ или **нет файла**. Воспроизведение: `gen_variants.py` + `run_variants.py` (фаза 3в). Исправление: общий `read_table(path)` (sniff `sep`, `decimal`, `encoding`, `errors="replace"` для task.md), `rglob` без учёта регистра, поиск train/test по структуре (train — файл со всеми колонками test + лишние).

**3. Нет id в шаблоне ответа / падение → копия шаблона с нулями** — `agent/task_parser.py::parse_task`, `solution.py::trivial_answer` (@n0h4ndy, @thenlaooo).
t02: `id=target=churned`, `KeyError`, AUC 0.5 вместо 0.856. Исправление: если в шаблоне одна колонка — ответ «по порядку строк test»; последняя ступень при любом сбое разбора — `blind_answer` (среднее/мода), а не копия шаблона.

**4. 93% бюджета простаивает** — `agent/loop.py`, `agent/fallback.py` (@n0h4ndy).
60-минутный прогон: 601 с работы из 3600 (17%); 19 экспериментов, запасных направлений всего 5. Воспроизведение: `scripts/run_local.py tasks/public/regression/task.md --minutes 60 --mock-llm`. Исправление — идеи роста Б.

**5. Дыры в реестре метрик** — `evaluation/metrics.py` (@dzigoku-ku).
Нет: F-beta/F2 (t10 → `recall`, F2 0.043 вместо 0.083), Brier, MASE, explained variance, Hamming, Jaccard, Spearman, linear kappa, «coefficient of determination». Первое упоминание побеждает: «ranked by RMSE» при раннем MAE → mae; «we used accuracy, but now RMSE» → accuracy. Воспроизведение: `runs/night/metric_probe.py`. Исправление: добавить F-beta (β из текста), Brier (= MSE вероятностей), правило «после but now/instead/ranked by — последняя».

**6. Ранжирование / top-k** — `evaluation/metrics.py`, `agent/task_parser.py`, `solution.py` (@dzigoku-ku, @n0h4ndy).
t16: «три товара через пробел» → одна метка, MAP@3 0.2295 (CV агента рапортовал 0.927 — ложная метрика). Вебинар: «ранжирование возможно». Исправление: распознавать `@k` и «через пробел»; ответ = top-k вероятностей классов.

**7. LLM-аналитик принимает id без проверки** — `agent/task_analyst.py::reconcile` (@n0h4ndy).
Ложный `id_column=cat_a` (не уникальный) принят → невалидный `submission.csv`. Исправление: принимать id только если уникален в test и (если есть шаблон) совпадает с его колонкой; метрику «меньше/больше» сверять с `greater_is_better` от LLM.

**8. Числа-строки (десятичная запятая в кавычках)** — `agent/task_parser.py::_guess_task_type`.
v02: target «object» → multiclass с 2200 классами и MAE; финал завис до сторожа. Исправление: если метрика «value» и target переводится в число (`str.replace(",", ".")`) — переводить; если классов > 0.5·строк — это не классификация.

**9. Нет промежуточной модели при очень большом train** — `solution.py`, `ml/experiment.py` (@thenlaooo, @marenkov17).
big3m (2 ядра, 25 мин): CV 863 с + финал не успели → ответ = среднее при готовой CV-модели. Исправление: после CV писать ответ из усреднённых фолд-моделей (предсказания на test «бесплатны»). На платформе риск при ≥ 30 млн строк.

**10. Окружение новичка** — `pyproject.toml`, `scripts/doctor.py` (@dzigoku-ku).
`uv run` при `default-groups=["dev"]` сносит группу `full` (xgboost/catboost исчезают, 30 тестов тихо пропускаются); `doctor.py` > 3 мин без вывода. Исправление: `default-groups=["dev","full"]` или `uv run --group full`; doctor — прогресс и `-k "not smoke"`.

### 5.2. Топ-5 идей роста
**А. Функция потерь под метрику** (= проблема 1). Проверка за час: ключ `objective` + 4 гипотезы, повторить `objective_probe.py` внутри агента. Эффект: до −27% MAPE, −54% pinball, −1…3% MAE. Риск переобучения на public: нет.

**Б. Простаивающие 165 минут: поиск + проверка + ансамбль.** После playbook — случайный/Optuna-поиск на схеме прогона до ~60% бюджета; затем топ-5 перепроверить повторной CV с другими seed (против «проклятия победителя»: `freq_encoding` принят при t=2.36 после ≈ 18 попыток) и усреднить модели. Проверка за час: 30-минутный прогон на 4 практических задачах с внешней отложенной частью (харнесс). Ожидаемый эффект: +0.5…2% метрики (бэггинг ×7 на diabetes: MAE 47.44 → 47.17, −0.6%, в пределах шума — проба других задач не дошла, убита по времени). Риск: переобучение выбора на CV — снимается отдельной отложенной частью.

**В. Роль LLM как «аналитика метрики и данных», а не генератора параметров.** Один структурированный вызов в начале и по одному раз в 20–30 мин: из task.md + профиля — какая функция потерь и какой порог под метрику, какие признаки, какая схема валидации; принятие тем же статистическим фильтром. Токены ↓: меньше повторных запросов (по ADR 0014 LLM-гипотезы дублируют playbook, ×2.55 по времени). Проверка за час: на t15/claims/t10 (метрика-зависимые) сравнить «LLM выбирает objective» с фиксированным правилом из А — **нужен ключ, мной не проверено**. Риск: нулевой для public, если правила А не зависят от задач.

**Г. Устойчивая загрузка и поиск файлов** (= проблемы 2, 3, 8). Мои 16 + 13 задач — готовый регрессионный набор (`research/night/gen_*.py` перенести в `tests/`). Эффект: 9/13 вариантов из нулевых в рабочие. Риск: нет.

**Д. Схема валидации на незнакомых данных: состязательная проверка.** Классификатор «train против test»: AUC ≈ 0.5 → kfold; высокий → отложить часть train, наиболее похожую на test, и сравнивать гипотезы на ней (работает и при смешанных форматах дат: на t07 схема не нашла время, `Схема валидации: stratified`). Проверка за час: на public regression (сдвиг по годам) и 8 practice. Ожидаемый эффект: честнее принятие гипотез (в experiments.md знак CV и честной части расходится в 41 из 113 пар). Риск для public: можно подогнать порог AUC — выбирать по синтетике.

**Проба идеи Д (состязательная проверка), `research/night/adversarial_probe.py`:** AUC классификатора train-против-test после отбрасывания колонок-«часов» (одна колонка отделяет train от test с AUC > 0.97).

| Задача | AUC | Колонка-«часы» | Что известно |
|---|---|---|---|
| public/regression | 1.000 | Year_Factor | сдвиг по годам, остальные признаки тоже сдвинуты |
| sales | 0.725 | date | test позже |
| public/multiclass | 0.870 | нет | дубликаты/кластеры |
| t14 | 0.670 | нет | новые категории в test |
| payments | 0.521 | date | test = следующий месяц |
| claims | 0.497 | record_no | сдвига нет (номер записи — не сдвиг) |
| cancer | 0.452 | нет | случайный split |

Вывод: без отбрасывания колонок-«часов» AUC = 1.0 даже там, где сдвига нет (claims: `record_no`), то есть наивный детектор бесполезен; с отбрасыванием он различает «сдвинуто» (≥ 0.67) и «случайно» (≈ 0.45–0.52). Оговорка: для строковых колонок я кодировал значения по порядку появления, а это протекает порядком строк — для строк нужен честный разбор дат, а не факторизация. Одной пробы мало для порога; выбирать порог по синтетике, не по public.
