# Ловушки для непокрытого: утечки трёх видов, мультиметка, ранжирование, 600k строк

Автор: roma (@Richi-Marqez) · 23.10.2026 · Генератор: `research/night/make_alien_tasks.py --set leak | uncovered` · Проверка ответа: `research/night/run_alien.py --set …`

## Зачем

На 15 «чужих» задачах гейта (`scripts/gate.py`) осталось 2 нуля, один из них — `leak_column_auc`. Это утечка одного вида: признак в test пуст, а в `task.md` прямо сказано, что он заполняется после события. Если проверку утечек в агенте (`ml/`, @marenkov17) настроить только на эту задачу, она поймает «пусто в test» и пропустит всё остальное. Ниже — три утечки **другой природы**. Ни в одной `task.md` не упоминает утечку, и признак в test заполнен.

Отдельно — три формата, которых нет ни в public, ни в 15 задачах гейта (вебинар: «несколько таргетов, ранжирование… может быть как в жизни»).

**В гейт эти наборы не входят.** Гейт считает нули ровно на 15 задачах `runs/night/alien` (тест `test_gate_set_stays_15_tasks`), иначе новая задача сразу дала бы «нулей стало больше». Когда проверка утечек появится в агенте, набор `leak` можно перенести в гейт отдельным PR.

```
uv run python research/night/make_alien_tasks.py --set leak         # → runs/night/leak/
uv run python research/night/make_alien_tasks.py --set uncovered    # → runs/night/uncovered/ (~90 МБ, 600k строк)
uv run python research/night/run_alien.py --set leak --minutes 5    # → runs/night/leak_results.jsonl
```

## Набор `leak` — три утечки разной природы

`meta["leak_columns"]` в `_answers/<задача>.json` — что надо отбросить. Ориентир `lgbm_default` в `run_alien` теперь считается **без** этих колонок: это DS, который заметил утечку. Поэтому «балл к сильному» > 0 возможен, только если агент утечку не взял. `lgbm_with_leak` — тот же LightGBM с утечкой: показывает, насколько ловушка бьёт по ответу.

Замер: LightGBM по умолчанию; CV — KFold-5 на train, test — настоящие ответы генератора.

| Задача | Природа утечки | Как обнаружить (чем отличается от `leak_column_auc`) | CV с утечкой / без | **Test с утечкой / без** |
|---|---|---|---|---|
| `leak_idlike_regno_auc` (ROC-AUC ↑) | **id-подобный признак**: `reg_number` — монотонный номер. В train он почти упорядочен по target (выгрузка отсортирована по статусу), в test — новый диапазон правее train | не называется id и заполнен в test. Сигнал — монотонный уникальный целый признак, по которому test целиком за пределами train | 0.980 / 0.766 | **0.612** / 0.764 |
| `leak_target_copy_mae` (MAE ↓) | **копия target**: `contract_sum` = цена ±1% в train. В test поле заполнено шаблоном из того же распределения, но без связи с target | состязательная проверка train/test его **не видит**: распределения одинаковые. Виден только «слишком хорошо» в train (corr ≈ 0.999, один признак объясняет всё) | 116 тыс. / 1.14 млн | **6.53 млн** (хуже тривиального 4.70 млн) / 1.12 млн |
| `leak_future_window_rmse` (RMSE ↓) | **будущее время**: `sales_3d_avg` — среднее продаж по окну [d−1, d+1], то есть в нём сам target и завтрашний день. В test будущего нет, поэтому значение заморожено на последней неделе train по магазину | валидация по времени эту утечку **не ловит**: окно строки целиком внутри фолда. Сигнал — признак в test постоянен внутри группы (магазина), а в train меняется каждый день | 10.15 / 10.84 | **17.72** / 11.54 |

**Чего ждём от проверки в агенте** (решение и реализация — за ml): правило, которое ловит все три утечки и `leak_column_auc`, но не выбрасывает честные сильные признаки. ⚠️ Риск ложной тревоги: на настоящих данных сильный признак бывает честным (например, значение прошлого периода). Поэтому лучше сравнивать в CV «с признаком / без», а не выбрасывать молча. Признаки, чтобы проверить себя на ложных тревогах: `cancer_binary_auc` (`worst_*` сильные и честные), public/regression.

## Набор `uncovered` — чего не было ни в public, ни в гейте

| Задача | Что проверяет | LightGBM по умолчанию / тривиальный на test |
|---|---|---|
| `multilabel_3targets_mean_auc` | **несколько бинарных таргетов в одном ответе** (≈30% / 10% / 3% положительных), вероятности, средний ROC-AUC по колонкам. В гейте мультитаргет только регрессионный (`multitarget_pinball90`) | 0.710 / 0.5 |
| `ranking_query_map5` | **ранжирование с `query_id`**: колонка ответа `score` ≠ имени таргета `relevant`, в test новые запросы (нужны группы в CV), у каждого запроса свой уровень `bm25`, MAP@5 считается по запросам. ⚠️ Метрика агента для ранжирования — приближение без групп (`evaluation/metrics.py`), своя проверка `run_alien` считает по запросам | 0.784 / 0.160 |
| `big_600k_time_dups_auc` | **большая таблица**: 600k строк train + 150k test, дата строкой `дд.мм.гггг`, test — следующий квартал, 15% полных дубликатов, `merchant` с 40k значений, ≈2–3% положительных и дрейф доли во времени. Проверяет `choose_validation` и поиск дубликатов на большой таблице (validation.md § 4.3), подвыборку CV `MAX_CV_ROWS`, время и RAM | ⏳ прогон агента |
