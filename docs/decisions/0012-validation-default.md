# 0012. Схема валидации по умолчанию: как устроен test, а не случайные фолды

- Дата: 2026-10-21 · Кто: @marenkov17 · Статус: предложено

## Контекст
Агент сравнивает гипотезы по кросс-валидации. Если фолды устроены не так, как скрытый test, CV выбирает не те гипотезы. В EDA (`docs/research/eda.md`) и playbook v1 (`docs/research/playbook-v1.md`) это уже видно: на регрессии test — следующий год, 35% строк — повторы зданий; на multiclass 45% train — полные дубликаты признаков. «cv и honest часто расходятся по знаку» — отсюда D1 в ADR 0008 и задача M-L2-1 (#29).

Теперь схема задаётся через `params.validation` (`ml/validation.py`): `kfold`, `stratified`, `group:<колонка>`, `group:duplicates`, `time:<колонка>`. Вопрос — какую брать по умолчанию на незнакомой задаче.

**Замер.** Те же гипотезы playbook считаются (а) обычной CV, (б) схемой, которую выбрал `choose_validation`. Для каждой — знак выигрыша над бейзлайном против **честной отложенной части** из playbook v1 (регрессия — последний год train, multiclass — группы дубликатов). Скрипт — LightGBM, 5 фолдов, `run_experiment` как у агента.

| Задача | Схема | Бейзлайн CV | log_target / balanced | extra_trees | slow_regularized | big_leaves | Знак совпал |
|---|---|---|---|---|---|---|---|
| regression (RMSE ↓) | kfold-5 | 41.81 ± 1.28 | −2.7% | −4.8% | −2.5% | +0.4% | **0/4** |
| | **time:Year_Factor-4** | 49.39 ± 4.11 | +0.0% | +3.0% | +1.8% | −2.0% | **4/4** |
| | *честно* (стенд playbook v1) | 48.40 | +2.1% | +12.2% | +8.0% | −3.7% | |
| multiclass (Macro F1 ↑) | stratified-5 | 0.5675 ± 0.0095 | +5.7% | −2.6% | +7.4% | −0.8% | 4/4 |
| | **group:duplicates-5** | 0.5767 ± 0.0200 | +6.3% | −5.9% | +3.9% | −2.2% | 4/4 |
| | *честно* (стенд playbook v1) | 0.5628 | +9.8% | −3.1% | +1.5% | −1.3% | |

На multiclass обе схемы угадывают знак; `group:duplicates` ближе по величине (средняя ошибка выигрыша 2.4 п.п. против 2.75) и не завышает «запоминающую» `slow_regularized` (+3.9% против +7.4% при честных +1.5%). Разброс фолдов вдвое больше — это честный шум, а не недостаток схемы.

**Optuna** (подбор на той же схеме, что и CV — ревью #115), regression, обучение на годах 1–4, проверка на годе 5:

| Что | CV | Честно (RMSE ↓) |
|---|---|---|
| бейзлайн | kfold-5: 45.24 ± 0.67 | 51.25 |
| Optuna на kfold | kfold-5: 44.38 ± 1.04 | 54.78 — хуже бейзлайна |
| Optuna на time:Year_Factor | time:Year_Factor-3: 49.18 ± 3.49 | **45.92** — лучше на 10% |

## Решение
Схему выбирает `choose_validation(spec, profile, train, test)` **один раз до цикла**, все гипотезы считаются в ней (ADR 0008, D1), правило принятия не сравнивает результаты разных схем (`agent/acceptance.py`):
1. Есть признак-время, и test лежит после train (5-й перцентиль test ≥ 95-го перцентиля train и медиана test строго позже) → `time:<колонка>`: скользящее окно вперёд, обучение на прошлом, проверка на следующем периоде. Из нескольких кандидатов — с «временным» именем, затем с меньшим числом значений.
2. Иначе ≥ 10% строк train — полные дубликаты признаков → `group:duplicates`.
3. Иначе `stratified` (классификация) / `kfold` (регрессия).

Правило — только про устройство данных (время, повторы), без названий колонок конкретных задач. На public: regression → `time:Year_Factor`, multiclass → `group:duplicates`; на tasks/practice: sales → `time:date`, network → `group:duplicates`, остальные — по умолчанию.

## Альтернативы
- **Всегда kfold/stratified.** Проще и меньше шум, но на регрессии 0 из 4 по знаку, а Optuna на ней подбирает утечку (54.78 против 51.25).
- **`group:<id объекта>`** (здание, клиент). Честнее kfold, но колонку объекта надо угадать по имени — на скрытой задаче это хрупко; повторы целиком ловит `group:duplicates`, а сдвиг во времени — `time`.
- **Выбирать схему по каждой гипотезе (LLM).** Скоры разных схем несравнимы — правило принятия перестанет работать. LLM может предложить схему, но менять её — только для всего прогона.

## Последствия
- CV по времени пессимистичнее и шумнее (49.4 ± 4.1 против 41.8 ± 1.3) и даёт меньше фолдов (периодов мало): правило принятия реже принимает гипотезы — это и нужно.
- Нужно подключить: **captain** — в `solution.py` перед бейзлайном `validation = choose_validation(spec, profile, train, test)` и `params["validation"]` у бейзлайна; **agent** — в `agent/loop.py` гипотеза без `validation` получает схему бейзлайна. Пока этого нет, всё считается как раньше (kfold/stratified).
- После подключения можно вернуть `optuna` в «Поддерживаемые params» (ревью #115): на честной схеме подбор полезен. До этого он остаётся скрытым.
- Не проверено: Optuna на `group:duplicates` (multiclass), задачи, где test — случайная выборка с дубликатами только внутри test.
