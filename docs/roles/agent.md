# Роль: LLM/agent-инженер (`agent`)

**Ты делаешь «мозг» агента**: как он понимает задачу, какие гипотезы предлагает, как решает, что делать дальше. Это главная часть кейса — AutoResearch.
**Твоя зона:** `agent/` (+ `agent/prompts/`). **Ревьюит тебя:** ml (если трогал оркестрацию — ещё капитан). **Ты ревьюишь:** — (по просьбе — PR капитана по циклу).
**Материалы:** [docs/resources/agent.md](../resources/agent.md) · **Модуль:** [agent/CLAUDE.md](../../agent/CLAUDE.md)

## 3.1 Установка (сверх [docs/install.md](../install.md))

Ничего тяжёлого не нужно — хватает ядра (`uv sync`), там уже `openai`, `pydantic`, `tenacity`.
Если захочешь попробовать LangGraph (есть в `requirements.txt`): `uv sync --group full` (⚠️ ~1.5 ГБ — на медленном интернете лучше в Codespaces).

Ключ LLM: получаешь у капитана **лично**, вписываешь в `.env` (Windows: `notepad .env`, macOS/Linux: `nano .env`).
**Проверка:** `uv run python scripts/doctor.py --role agent --llm` → `✅ запрос к LLM`.

## 3.2 Git в твоей роли

Общий гайд — [docs/git-guide.md](../git-guide.md). Для тебя важно:
- Ветки: `agent/<задача>` — например `agent/llm-hypotheses`, `agent/prompts`.
- Ты чаще всех стыкуешься с ML-инженером: формат `Hypothesis.params` — общий. Перед PR, который добавляет новые ключи `params`, — `/sync-check`.
- Промпты — обычные файлы в git: в ревью видно, что поменялось в «мышлении» агента. Меняешь промпт → в описании PR пиши, как изменилось поведение на прогоне.
- Посмотреть, как твой цикл работает с кодом ML-инженера из его ветки: `gh pr checkout <номер>` (git-guide, раздел 8).

## 3.3 Рабочие инструменты по кейсу

| Инструмент | Зачем тебе |
|---|---|
| Qwen (через `OPENAI_BASE_URL`) | единственная разрешённая LLM; 600 ₽/день на всю команду |
| `openai` (Python SDK) | клиент к OpenAI-совместимому API Qwen — как в `reference/baseline.py` |
| `pydantic` | проверка ответа LLM: JSON → `Hypothesis`, мусор отсекается |
| `tenacity` | повторы запросов при сетевых сбоях |
| `agent/llm_client.py` | наш клиент: кэш ответов (`LLM_CACHE_DIR`), учёт ₽ (`LLM_RUB_LIMIT`), режим без LLM (`LLM_MOCK=1`) |
| `research/playbook.yaml` | готовые гипотезы — fallback и few-shot примеры для промпта |
| `runtime/sandbox.py` (делает капитан) | исполнение кода, который пишет LLM |
| `langgraph` (опционально) | если захочешь граф ролей агента; ⚠️ не обязателен — простой цикл на Python часто надёжнее |
| `scripts/run_local.py`, workflow run-agent | прогон агента на задачах (локально / в облаке GitHub) |

### L0 — разогрев

#### A-L0-1 · Разогрев — запустить агента и разобраться в цикле · CP0

*Зачем:* Понять, как сейчас устроены разбор задачи, гипотезы и цикл, прежде чем менять.

1. `uv run python solution.py tasks/public/multiclass/task.md` с `AGENT_TIME_BUDGET_SEC=300` и `LLM_MOCK=1`.
2. В Claude: `/explain agent/loop.py` и `/explain agent/llm_client.py`.
3. Первый маленький PR — тест на `LLMClient.chat_json` (JSON в ```json, мусор, пустой ответ) через сабагента test-writer.

**Готово, когда:**
- [ ] Твой первый PR в dev слит, ты можешь объяснить цикл AutoResearch своими словами.

### L1 — базовые

#### A-L1-1 · Подключить настоящий Qwen · CP2

*Зачем:* Без проверенного вызова LLM нельзя строить умную часть.

1. Получить ключ у капитана лично, вписать в .env (не в чат!).
2. `uv run python scripts/doctor.py --role agent --llm` — ✅ запрос к LLM.
3. Замерить время ответа и токены на типичный промпт, записать в docs/experiments.md.

**Готово, когда:**
- [ ] doctor с `--llm` зелёный, известны скорость и стоимость одного запроса.

**🔗 Стыковка:** captain выдаёт ключ; цена токенов — из ответа организаторов (C-L1-2).

#### A-L1-2 · Папка промптов и формат ответа LLM · CP3

*Зачем:* Промпты должны быть файлами, которые видно в ревью, а ответы — проверяемыми.

1. Создать agent/prompts/ (system.md, hypotheses.md) с плейсхолдерами для TaskSpec, DataProfile, истории.
2. Описать в промпте JSON-формат ответа, совпадающий с Hypothesis, и пример (few-shot из playbook).
3. Тест — рендер промпта на stub-данных.

**Готово, когда:**
- [ ] Промпты в файлах, тест рендера зелёный.

### L2 — основные

#### A-L2-1 · Гипотезы от LLM в propose_hypotheses · CP3

*Зачем:* Главная «умная» часть кейса — агент сам формулирует гипотезы.

1. LLM получает: тип задачи, метрику, сжатый DataProfile, историю итогов экспериментов.
2. Ответ → валидация через Hypothesis → отброс невалидных и повторов → fallback на playbook.
3. Тесты с подменой LLM (хороший ответ / мусор / None) — цикл не падает.

**Готово, когда:**
- [ ] При `LLM_MOCK=0` агент проверяет гипотезы, которых нет в playbook; при `LLM_MOCK=1` всё работает как раньше.

**🔗 Стыковка:** ml — список поддерживаемых params (ежедневно 13:00).

#### A-L2-2 · Память экспериментов и рефлексия · CP3

*Зачем:* Агент должен помнить, что уже пробовал, и понимать, почему не сработало.

1. Сжатое представление истории для промпта (таблица гипотеза → метрика ± std → принята/нет).
2. После неудачи — короткая «рефлексия» LLM (почему, что попробовать иначе), сохраняется в историю.
3. Ограничить длину контекста (последние N + лучшие K).

**Готово, когда:**
- [ ] Промпт укладывается в лимит, повторных гипотез нет на прогоне 30 минут.

#### A-L2-3 · Честное правило принятия гипотезы · CP4

*Зачем:* Сейчас порог шума отсёк улучшение 41.81 → 41.62 на регрессии; нужно правило, которое не пропускает шум, но не душит реальные улучшения.

1. Сравнивать по фолдам попарно (одинаковые разбиения), а не только средние.
2. Подобрать правило на истории экспериментов (с research), записать решение в docs/decisions/.

**Готово, когда:**
- [ ] ADR с правилом, тест на граничные случаи.

**🔗 Стыковка:** research — данные экспериментов для проверки правила.

### L3 — на победу

#### A-L3-1 · LLM пишет код признаков (в песочнице) · CP4

*Зачем:* Признаки, придуманные под конкретные данные, — то, чего не умеет обычный AutoML.

1. Новый вид гипотезы: `kind: features` с полем code (функция df → df).
2. Исполнять только через runtime/sandbox (C-L2-1), проверять результат на train-фолдах.
3. Защита от утечек — код не видит target теста.

**Готово, когда:**
- [ ] На харнессе хотя бы одна задача улучшилась за счёт сгенерированного признака.

**🔗 Стыковка:** captain — песочница; ml — применение признаков внутри CV.

#### A-L3-2 · Роли внутри агента — аналитик, генератор, критик · CP4

*Зачем:* Критик отсеивает гипотезы с утечками и «подгонкой» до того, как на них потрачено время.

1. Разделить промпты по ролям; критик проверяет гипотезу по чек-листу (утечка, универсальность, цена по времени).
2. Сравнить на харнессе с одноролевым вариантом.

**Готово, когда:**
- [ ] Решение (оставляем или нет) записано в docs/decisions/ с цифрами.

## 3.5 Claude Code в твоей роли

- **Скилл** `agent-llm` подключается сам, когда работаешь в `agent/`: рецепт «гипотезы от LLM», принципы для маленькой модели.
- **Команды:** `/next-task`, `/sync-check` (перед новыми `params`), `/pre-pr`, `/explain`.
- **Сабагенты:** `test-writer` — тесты с подменой LLM; `ml-mentor` — «какие гипотезы имеет смысл давать агенту для несбалансированных классов?»; `code-reviewer` — перед PR.
- **context7** — актуальная документация `openai`, `pydantic`, `langgraph`: «use context7, как в openai 1.68 задать timeout и max_retries».
- **Опционально:** `pyright-lsp` (типы в Python), `learning-output-style` (если хочешь учиться, а не получать готовое) — см. SETUP_CLAUDE.md.

Примеры запросов:
> «Режим подсказки. Хочу, чтобы propose_hypotheses спрашивал LLM. С чего начать?»
> «Сгенерируй тест: LLM вернула JSON в ```json и один невалидный элемент — цикл не должен упасть»
> «Сколько токенов уходит на промпт agent/prompts/hypotheses.md с историей из 20 экспериментов?»
